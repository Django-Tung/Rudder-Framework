# 第一部分 · 总

## 1. 背景

Rudder 当前在**流程可控性**上做得扎实——状态机、门禁、依赖闭包、证据留痕、技能单源投影，这套设计有效对冲了「AI 跑偏、吹牛、乱改」。

但对着产品目标逐条比对：

| 目标 | 现状 | 根因 |
|---|---|---|
| **好看** | ❌ 零约束 | 规则只管「用什么写」，不管「长什么样」 |
| **符合需求** | ⚠️ 半闭环 | 校验的是文档引用完整性，不是代码与需求的一致性 |
| **能展示给客户** | ❌ 无准备 | 无假数据标准、无演示动线、无资源策略 |

**共同根因一句话**：框架默认「用户有判断产出质量的能力」，所以把所有检查都做成了**结构性校验**——而目标用户恰恰不具备这个能力，他看得懂页面好不好看，看不懂 `check:req` 拦住了什么。

本次改造的取向是：**把「好看」和「能演示」从 AI 的自由发挥，转变为规则与代码保证；把「符合需求」的最后一环补上人工可核对的凭据。** 不削弱已有门禁，不改动状态机。

## 2. 目标与非目标

### 目标

| # | 目标 | 判定 |
|---|---|---|
| G1 | 视觉产出可复现、跨 REQ 不漂移 | 同类元素外观一致；`src/` 中无任意色值 |
| G2 | 新手能在风格选择处**做出选择或说「你决定」** | 不卡住 |
| G3 | 每条 AC 都能被人工核对出「做了 / 没做」 | 核对表行数与 AC 数一致（机器校验） |
| G4 | 客户面前不出戏 | 无占位文案、无图裂、无 `rudder-framework` 标题 |
| G5 | 新手不用理解状态机就能走完流程 | 一页纸决策树 |
| G6 | 演示环境零外网依赖 | 断网可完整演示 |

### 非目标

- ❌ 不做部署、导出 PDF、录屏、在线分享（已确认本地演示即可）
- ❌ 不做「跳过 PRD 审批」逃生口（已确认保留门禁）
- ❌ 不做浏览器自动化截图核对（已确认人工核对）
- ❌ 不做演示者备注视图 / 全屏演示模式（已确认按常规网页习惯）
- ❌ 不做强制响应式双端（已确认「明确了再做」）
- ❌ 不削减 Hermes 投影（已确认保持现状）
- ❌ **不引入带预置视觉风格的组件库**——见 §4.2

# 第二部分 · 分

## 5. 模块一：视觉质量

> 对应 [`proposals/visual-quality.md`](proposals/visual-quality.md)。**这是本轮改造中收益最大、也最复杂的一块。**

### 5.1 设计令牌体系（三层结构）

```text
第 1 层  设计令牌 @theme        ← 机器可读，AI 只能引用，不得自造
第 2 层  预设风格包             ← 人类可选，新手回答「这两个要哪个」
第 3 层  通用组件               ← 跨 REQ 复用，消灭风格漂移
```

**为什么三层都要**：只有规范文字会被 AI 绕过；只有组件库无法覆盖长尾场景；只有令牌无法保证复用。三层缺一不可。

#### 令牌草图（D3，待评审）

**P4 · 品牌派生** — 客户有自己的品牌规范时

不是第四套固定令牌，而是一条**派生规则**：用户提供品牌主色 + `MASTER-PRD.md` 记录，按 P1 的档位结构（50/100/500/600/700）派生，主色同时用于 `--color-brand-*`。**其余令牌（字阶、间距、圆角、阴影）沿用 P1**，只有色板被替换。这样保证客户品牌色的原型**仍然与其他 REQ 一致**。

> ⚠️ **草图需你评审**：色值、字阶、圆角的具体数字是我按通行设计规范给的，**涉及品牌观感，不是我能替你定的**。请逐套过一遍，特别是 P2 的深色是否值得单独做一套（它的工作量最大，但很多企业客户偏好深色数据台）。

#### 令牌落点

| 内容 | 位置 |
|---|---|
| `@theme` 令牌定义（**唯一色值来源**） | `src/index.css` |
| 预设切换 | 单一 TS 文件记录「当前生效预设 → 对应哪套 `@theme`」，改预设 = 改该文件 |
| 令牌→class 名映射与语义别名 | `src/design/tokens.ts`（导出常量，如 `BTN_PRIMARY = 'bg-brand-600 text-white rounded-md ...'`） |
| 预设图示 | `docs/styles/p1-light-console.md` 等 3 篇（ASCII 线框 + 色板 + 适用场景） |

#### 机器约束

```js
// eslint.config.js 新增：src/ 下禁止任意十六进制色值
'no-restricted-syntax': ['error', {
  selector: "Literal[value=/#[0-9a-fA-F]{3,8}/]",
  message: '颜色必须来自 src/index.css 的 @theme 令牌，不得硬编码色值',
}]
```

**需要收敛误报**：SVG 的 `fill="#fff"` 会被命中。落点时需限定该规则只作用于 `.tsx` 中的 JSX 属性，或为 SVG 开例外。**这一条在实施阶段验证，方案里先标注为风险。**

**组件基线**（D4：基础件预置，业务件边做边沉淀）

| 层 | 组件 | 来源 |
|---|---|---|

| **第二层 · 边做边沉淀** | 业务组件（供应商卡片、订单表格……） | 各 REQ implement 阶段产出；产生时**检查是否应下沉到第一层** |

> 同类交互元素**必须**使用 `src/components/` 中的组件。确需新建的，须在 `implement.md` 说明现有组件为何不适用。
> 新组件若具备通用性，**必须**下沉到第一层。

### 5.3 风格选择流程改造（D1 / D2 / G2）

**现状**：`rudder-plan` 问「数据密集型工作台 / 轻量内容型 / 品牌主导 / 自定义」——纯文字，新手无法成像。

**改为**：

```text
Agent 展示 docs/styles/ 下的 3 张预设图示（带色板 + 线框 + 适用场景）
  ↓
问用户（中文，二选一）：
  ① 选 P1 / P2 / P3 中的哪一个？
  ② 或者直接说「你决定」
  ↓
选 ② → 采用 P1（默认），在 MASTER-PRD 记「用户未指定，采用默认预设 P1 · 清爽后台」
  ↓
不写「待用户确认」，流程不卡
```

**`MASTER-PRD.md` §1 新结构**：

```yaml
## 1. UI 主风格
- 预设：P1 · 清爽后台        # P1 | P2 | P3 | BRAND
- 来源：用户选定 | 用户未指定，采用默认
- 令牌集：src/index.css @theme（随预设同步）
- 例外：<单个 REQ 的例外及原因，无则「无」>
- 确认日期：YYYY-MM-DD
```

## 6. 模块二：需求一致性

> 对应 [`proposals/requirement-fidelity.md`](proposals/requirement-fidelity.md)

### 6.1 AC 可判定化（第一层，一切的前提）

在 `.rudder/requirement/acceptance.md` 新增：

> **可判定性要求**：每条 AC 的 `Then` 必须包含**可观察的具体行为**——界面上出现的文字、元素、状态、数值。不得只写主观判断。

| 判定 | 例子 |
|---|---|
| ❌ 不可判定 | 「页面要美观易用」「错误状态要友好提示用户」「加载要快」 |
| ✅ 可判定 | 「接口返回 500 时，列表区域显示左侧红色边框的 Alert，文案为『加载供应商失败，请稍后重试』，右侧提供『重试』按钮，点击后重新请求」 |

`rudder-plan-confirm` 把此项列为**检查项**：写不出可观察行为的 AC，退回重写。

**对业务用户的价值**：写不出可观察行为的 AC，恰恰说明他自己也没想清楚要什么——这正是澄清该发生的地方。

### 6.2 实现核对表（第二层，D5 / D8）

`implement.md` 新增一节：

```markdown
## AC 实现核对表

| AC | 实现位置 | 核对结论 |
|---|---|---|
| AC-1 列表加载中显示 6 行骨架屏 | `src/pages/SupplierList.tsx:42` | ☐ 待确认 |
| AC-2 空数据时显示引导文案与按钮 | `src/pages/SupplierList.tsx:78` | ☐ 待确认 |
```

**分工（D8）**：AI 填「实现位置」——**填不出来即代表未实现**；「核对结论」列由 AI 留空 `☐`，**用户在浏览器上核对后自己勾**。

**机器校验**（`check-req.js` 新增 I3）：

```text
I3（AC 实现定位）：implement.md 中「AC 实现核对表」的行数
                   必须等于 plan.md 中 AC-N 的条数，且编号一一对应。
                   实现位置为空 → 校验失败。
```

> **为什么这条有效**：它不需要浏览器自动化能力，就把「每条 AC 都必须落到具体代码行」变成了一条**确定性断言**。AI 无法靠勾选 tasks.md 蒙过去——蒙过去也必须填出一个真实的文件行号，而行号填错时用户核对会发现。

### 6.3 路由（D7）

引入 `react-router`。解决的问题：

- 多页跳转行为在 REQ 间一致（当前由 AI 每次手搓）
- **浏览器前进 / 后退可预期**——会议室投屏时客户或演示者点返回不会出戏
- `layout.md` 里写的路由变成可验证的事实，而非填空题

### 6.4 响应式口径统一（D6）

| 位置 | 现状 | 改为 |

## 7. 模块三：演示准备

> 对应 [`proposals/demo-readiness.md`](proposals/demo-readiness.md)

### 7.1 假数据基线（**优先级最高，成本最低**）

AI 当前默认生成 `张三` / `测试数据1` / `item-001` / `2024-01-01`。客户第一眼就出戏——注意力从「你的方案怎么样」转到「这东西是不是真的」。

**`MASTER-PRD.md` 新增一节**（§1 之后）：

```yaml
## 2. 业务场景与假数据基线

- 业务领域：<如：工业品供应链 / 医美连锁 / 企业培训>
- 典型机构与角色：<如：华东机电、张明（采购主管）>
- 真实感数值区间：<如：订单金额 5 千 ~ 80 万；交期 3 ~ 45 天>
- 状态流转真实形态：<如：草稿 → 待审核 → 已通过 → 已终止；禁用 active/inactive>
- 占位内容黑名单：Lorem ipsum / test / 示例 / xxx / 连续整数日期 / 公司A / 用户1
- 列表数据量下限：≥ 12 条（须填满首屏并有滚动余量）
```

最后一条常被忽略但影响极大：**只有 3 条数据的列表，客户无法感知「这是个有规模的产品」**，也看不出滚动和分页表现。

**`/rudder-plan` 与 `/rudder-import` 入口提问时**，若无基线则先确认（沿用现有「主风格确认」的提问节奏，不新增一道流程）。

**`plan.md` 模板 §5.2 Mock Schema 增加约束**：

> Mock 数据必须符合 `MASTER-PRD.md` 的假数据基线。禁止黑名单内容；列表类页面数据量 ≥ 基线规定的下限。
> 错误注入数据同样须符合基线（错误文案也走业务语感，不写「接口错误」）。

### 7.2 本地资源规范（D11）

**决策：零外链。** 会议室投屏网络不可靠，外链图裂当场就是事故；全本地则断网也能完整演示——这条直接达成 G6。

**规则**：

| 资源类型 | 规定 |
|---|---|
| 公司 Logo / 客户品牌素材 | 用户放入 `public/brand/`。**未提供时用统一占位 SVG**，不得外链 |
| 商品图 / 头像 / 照片 | 用户放入 `public/assets/`；未提供时用 `PlaceholderImage` 组件生成**本地 SVG 占位图**（统一几何风格，随令牌配色） |
| 空状态插画 | **统一一套**（`src/components/` 内固定），禁止 AI 每次现画——风格必然漂移 |
| 图表 | 纯 SVG/CSS 绘制，不引第三方图表库 |
| 全部外部资源 | **禁止 `<img src="http...">` 等任何 http(s) 外链** |

**机器约束**：`eslint.config.js` 增加规则，拦截 `src/` 中 `<img>` / `<source>` 的外链 `src`。这把 G6 从约定变成了断言。

**需在实施时验证的风险**：`src/` 中可能出现 SVG 的 base64 data URI——这类**是本地合法的**，规则需放行 `data:`，只拦 `http(s):`。

### 7.3 演示动线（`implement.md` 新增节）

由 Implement 阶段生成，**因为 AI 掌握完整页面结构，能判断最有说服力的路径**：

```markdown
## 演示动线

- 开场页：<哪个页面，为什么>
- 路径：
  1. 点击「...」→ 进入 <...>，说明：<...>
  2. ...
- 收尾画面：<回到哪个页面>
- 兜底：<某交互没生效时跳到哪个页面>
```

### 7.4 演示检查清单（D12：不阻断）

新增 `docs/demo-checklist.md`，`/rudder-commit` 完成后 Agent **主动提示但不阻断**：

- [ ] `npm run dev` 启动无报错
- [ ] 浏览器已最大化或按会议室投屏调整（≥1280px 宽）
- [ ] 按演示动线完整走一遍，无空白页 / `undefined` / `NaN`
- [ ] 所有页面 mock 数据非空，抽查 3 条符合假数据基线
- [ ] 无图片加载失败

- [ ] 已了解：加载等待与错误提示是**模拟网络行为**，用于展示加载与异常处理设计

> 最后一条是 D9/D10 的落点：Agent **不生成话术**，只在清单里提示用户这一事实，由用户临场自行说明。

**P0 → P1 必须先做**（其余全部依赖它们的规则与白名单）。P2 与 P3 价值最高、依赖最多，建议优先并行。P4 的假数据基线部分（P4-a）**不依赖任何前置，可随时插入**——它成本极低、收益极大。

## 10. 风险登记

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | eslint 色值规则**误报** SVG 的 `fill="#fff"` / base64 data URI | P1 阻塞 | 规则限定作用域；P1 完成前必须先写测试用例验证 |
| R2 | 外链拦截规则**误报** CDN 字体或第三方脚本 | P4 阻塞 | 明确只拦 `<img>/<source>` 的 http(s) src；字体策略一并明确 |
| R3 | 令牌草图（D3）**用户评审后要求大改** | P2 返工 | **P1 只落地 P1 默认预设**，P2/P3 延后到草图确认后再做 |
| R4 | 通用组件基线过大，第一层组件有大量无人使用 | 维护负担 | P2 只做**首批必需**件（Button/Input/Card/Skeleton/EmptyState/ErrorState/Table），Modal/Tabs 等按需再加 |
| R5 | 人话播报（D16）在长对话中被 AI 省略 | G5 落空 | 写入技能的 STRICT 段；并让 `check-req` 无法校验——**这是已知的弱约束，靠 review 发现** |
| R6 | AC 核对表变成**纯打勾仪式**，用户不认真核对 | G3 落空 | 「实现位置」由 AI 填且机器校验，降低用户负担；结论列不预填，强制用户自己勾 |
| R7 | 假数据基线在**已有项目**中缺失 | 老项目无法套用 | 规则区分「新项目必填 / 老项目首次变更时补填」 |
| R8 | 引入 headless 库被后续误用为「可以装 UI 库」 | 视觉失控 | 宪法措辞收紧 + **逐个登记白名单**，新增须人工确认 |
