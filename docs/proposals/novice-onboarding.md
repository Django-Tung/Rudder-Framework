# 落地方案 · 新手引导与状态可读性

> 对应评审报告 [`../review-2026-10-02.md`](../review-2026-10-02.md) §4.1 / §4.2 / §4.3 / §4.4
> 目标用户：**产品 / 业务人员，不懂前端**。
> 原则：**不削弱框架内部的状态机**，而是在**用户侧加一层人话视图**。

---

## 问题复述

一个业务人员第一次使用前要理解：7 个命令、2 条入口路径、IMP 管道的 4 个状态、每 REQ 6 个文档 + IMP 4 个文件、双层状态（顶层 4 态 × 产物 7 态 × `stale` 布尔）。

这套体系的设计是好的——它防的是 AI 跑偏。但对目标用户，**状态名本身是纯噪音**，而他每天都会在对话里看到它们。

`docs/getting-started.md` 是一份**平铺的操作手册**（10 节，约 300 行读完），它说「怎么做」，但没说：

- **「我现在该做什么」**——每一步都要求用户自己判断前置条件是否满足
- **「出错了怎么办」**——没有决策树

---

## 方案

### 1. 增加「人话状态映射」层（**成本最低，收益最高**）

内部状态机**完全保留**。只是要求 Agent 在每次对话输出时，附带一句人话说明。

在 `.rudder/workflow/states.md` 增加一张映射表：

| 内部状态 | 对用户说 |
|---|---|
| `PLANNED` / `DRAFT` | 📝 需求还在起草，你可以随便改 |
| `APPROVED` | ✅ 需求已定稿，AI 开始可以动手写代码 |
| `IMPLEMENTING` | 🔨 正在写代码 |
| `IMPLEMENTED` | 🧪 代码写完了，你可以打开看看满不满意 |
| `COMMITTED` | 📦 已提交存档 |

并在各技能中要求：**每次状态变化时，用人话播报一次**。

> **为什么不削弱状态机**：状态机的价值在于**机器可校验**（`check:req` 依赖它），与用户能否理解无关。削弱它会直接破坏框架的核心设计。加一层映射则零成本。

### 2. 给「现在该做什么」一个明确答案

新增 `docs/quickstart.md`——**一页纸**，回答业务用户的四个问题：

```text
我想做一个原型          → 跳到这里
我现在能做什么          → 跳到这里
AI 停下来了要我回答问题  → 跳到这里
做完了，我怎么看          → 跳到这里
```

结构上是**决策树**而非线性手册：

```text
你手上有完整需求文档吗？
├── 是 → /rudder-import 需求文档.docx → 暂停等你确认拆分 → 确认后对每个 REQ 跑 /rudder-plan
└── 否 → 直接 /rudder-plan 用一句话描述你想做什么
          ↓
      AI 会反问你 1-3 个问题（认真回答，这决定成品质量）
          ↓
      AI 给你看 plan.md（需求文档）+ layout.md（页面草图）
      ↓
      ✅ 你看得懂吗？→ /rudder-plan-confirm REQ-001，然后回一句「PRD 批准」
          ↓
      /rudder-implement REQ-001
          ↓
      打开 http://localhost:5173 看效果
          ↓
      不满意？→ 说清哪里不对，AI 会改
      ↓
      满意？→ /rudder-commit REQ-001
```

**关键改动**：现有 `getting-started.md` 是 10 节平铺流程，quickstart 是**决策树**。前者是写给「已经决定要用这个工具」的人的，后者是写给「还不知道该走哪条路」的人的。

### 3. 明确「什么时候可以跳过」

新手最大的焦虑是「我是不是做错步骤了」。建议在 quickstart 里明确写出：

| 场景 | 能不能跳过什么 |
|---|---|
| 只有个模糊想法 | **必须**走 `/rudder-plan`，别用 import |
| 只想先看看效果 | 可以先跑 `/rudder-implement` 的**草稿模式**？—— ❓ **待你确认是否要提供这种逃生口** |
| 需求很小、很清楚 | 可以…… ❓ **待确认** |
| 已经返工多次 | 可以走 `/rudder-adjust` 快速修，**不要**走 `/rudder-change` |

最后一行是现有文档里**缺失的高价值信息**：`/rudder-adjust` vs `/rudder-change` 的区别（README 用了一整段 L346 解释），对新手应该是**一句话判断**：

> **需求本身没变，只是做得不对 → adjust**
> **需求本身变了（多了一个功能）→ change**

### 4. 修掉文档里的失效内容（**应当立即修**）

| 位置 | 问题 | 修法 |
|---|---|---|
| `docs/getting-started.md` L44-45 | `git clone <项目地址>` / `cd ProtoSource` — 占位符 + 目录名与实际不符（实际为 `Rudder-Framework`） | 填真实地址，或明确标注「请替换」并统一目录名 |
| `README.md` §2 L43-44 | 目录树列出 `.rudder/verification/` 与 `.rudder/review/`，**这两个目录不存在** | 删除或补建 |
| `README.md` §2 | `.rudder/agents/` 写「各 runtime 的读取约定」，实际只有 `claude-code.md` | 标注或补齐 |
| `docs/getting-started.md` §6 | 表格中「Implement」**重复出现两次**（L159、L160），一条讲编码一条讲检查 | 合并或改名为「Implement（编码）」/「Verify（校验）」 |

> L159-160 那个重复行会让用户以为要做两件事，是个小但真实的困惑源。

### 5. 增加「出错了怎么办」决策树

现有文档完全没有这部分。新手遇到「AI 没按我说的做」时无从下手。

新增章节，覆盖**新手真正会遇到**的几种情况：

| 症状 | 大概率原因 | 怎么办 |
|---|---|---|
| AI 说「需要你确认」，然后停住 | 缺澄清答案 | **回答它问的那个问题**，不要重复原话 |
| AI 说「不能修改代码，等你批准」 | `plan.md` 还是 `DRAFT` | 走 `/rudder-plan-confirm` |
| AI 说「依赖未满足，REQ-002 的 plan 还是 DRAFT」 | 依赖顺序错了 | 先完成 REQ-002，或让用户改 `deps` |
| 页面报错 / 需求没实现 | 实现缺陷 | 说明复现步骤，**不要**用 `/rudder-change` |
| 做出来的东西完全不对 | 需求描述太模糊 | 走 `/rudder-change` 或开新 REQ |
| AI 反复问同一个问题 | — | 明确给出答案或默认值 |

### 6. Hermes 双投影的取舍（评审报告 §4.4）

**现状**：`skills/` 7 个源 → 投影为 `.claude/commands/` 7 个 + `.hermes/skills/` 7 个 = 14 个文件。

**问题**：对新手是 7 个而不是 14 个概念，多出的 7 个文件是纯噪音，且新手几乎不会用到第二个 runtime。

**三个选项**：

| 选项 | 说明 |
|---|---|
| A. 保持现状 | 维护成本是脚本自动的（`sync-skills`），实际负担不大 |
| B. 若 Hermes 暂无用户，暂停投影 | 需改 `sync-skills.js`，后续要补回 |
| C. 保持现状，但在 README / quickstart 中**只呈现 Claude Code** | 零改动，Hermes 作为高级选项折叠 |

**我倾向 C**（零成本、不破坏架构、消除新手噪音），但这取决于你 Hermes 的规划。

## 验收标准

- [ ] 一个**从未用过**该工具的业务人员，只读 `quickstart.md` 就能走完第一个 REQ
- [ ] 他全程**不需要**理解 `IMPLEMENTING` / `OUTDATED` / `STALE` 这些词就能完成流程
- [ ] 他遇到 AI 停住时，**知道下一步该做什么**（而不是反复重述需求）
- [ ] 他能一句话判断该用 `adjust` 还是 `change`
- [ ] `README.md` 中每一条目录 / 文件引用都真实存在
