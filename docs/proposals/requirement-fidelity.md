# 落地方案 · 需求一致性

> 对应评审报告 [`../review-2026-10-02.md`](../review-2026-10-02.md) §2.1 / §2.2 / §5.1
> 目标：把「符合需求」从**引用完整性**升级为**语义一致性**——让「做出来了」不再等于「文档打勾了」。

---

## 问题复述

`check:req` 的 I1 断言「每条 AC 被某个 task 引用」，I2 断言「`implement.md` 为 `COMPLETED` 时 `tasks.md` 无未勾选项」。

这两条查的是**文档之间的引用关系**，不是**代码与需求的一致性**。因此 AI 可以勾完所有任务、5 条 npm 命令全绿、`check:req` 通过，而页面和 AC 描述的完全不是一回事——**没有任何一步要求打开浏览器看一眼**。

对不懂前端的用户，这尤其危险：他最依赖这套检查，却完全无法判断「检查通过」意味着什么。

---

## 方案：三层递进的对账

### 第一层：AC 可判定化（文档侧，成本最低，收益最大）

当前模板允许写出**无法判定真伪**的 AC。例如：

> ❌ 「页面要美观易用」
> ⚠️ 「错误状态要友好提示用户」
> ✅ 「接口返回 500 时，列表区域显示红色左边框的 Alert，文案为『加载供应商失败，请稍后重试』，并提供『重试』按钮，点击后重新请求」

**改法**：在 `.rudder/requirement/acceptance.md` 中明确 AC 的**可判定性要求**，并在 `plan-confirm` 阶段把 AC 列为检查项：

> **AC 可判定性检查**：每条 AC 的 `Then` 必须包含「可观察的具体行为」（界面上出现的文字、元素、状态、数值），不得只写主观判断。凡是写不出具体可观察行为的 AC，退回重写。

**为什么优先做这个**：只要 AC 是可判定的，「让 AI 打开浏览器核对」才有意义；否则核对也无从下手。**这一层是后面两层的前提。**

对业务用户的好处：写不出可观察行为的 AC，恰恰说明**他自己也没想清楚要什么**——这正是澄清该发生的地方。

### 第二层：实现后的视觉核对（Verify 环节）

在 Implement 阶段的质量检查之后，增加一步**必须看渲染结果**的核对。

#### 可行性确认

| 手段 | 成本 | 说明 |
|---|---|---|
| **Agent 自行启动 dev server + 截图** | 中 | 需要浏览器自动化能力（当前依赖里没有） |
| **人工核对清单** | 低 | 由用户对照 AC 逐条打勾，可选 |
| **保留现状 + 明确告知** | 0 | 承认这是人工环节，不假装自动化 |

#### 推荐形态（混合）

`implement.md` 的自检清单中增加**「AC 逐条核对表」**：

| AC | 实现位置（文件:行） | 核对方式 | 结论 |
|---|---|---|---|
| AC-1 列表加载中显示 6 行骨架屏 | `src/pages/SupplierList.tsx:42` | 人工 / 截图 | ✅ |

要求：**每条 AC 必须填「实现位置」**。填不出来 = 没有实现。这是一条**可机器检查**的规则（检查表格行数与 AC 编号一致），且不需要浏览器自动化能力。

若你希望进一步自动化（Agent 自己截图核对），则需要引入浏览器自动化依赖——**这属于放开项，见评审报告 §5.3 的同类提案，待你确认**。

### 第三层：`layout.md` 的可执行化

**现状**：ASCII 线框只能表达区域划分，表达不了视觉质感与响应式行为。

**改法（分级，不要求一步到位）**：

| 级别 | 做法 | 成本 |
|---|---|---|
| L0（现状） | ASCII 线框 | 0 |
| **L1（建议）** | 保留线框，但**强制填写窄屏行为的具体映射**：「桌面端侧栏在 <768px 时 → 收进顶部汉堡菜单」；禁止只写「自适应」 | 低 |
| L2 | 线框之外增加「间距与层级标注」：主要区域之间的相对间距档位 | 低 |
| L3 | 用真实 HTML 骨架（只有布局、无业务逻辑）替代线框，可直接渲染查看 | 中高 |

**建议先做 L1**：它不需要任何新能力，只是把一句空话变成可核对的描述，而且直接对应「客户演示时在窄屏上看到的东西变形」这个高频演示事故。

## 关于路由（评审报告 §5.1）

`plan.md` 与 `layout.md` 模板都强制要求填写「路由」，但 `package.json` 中**没有路由库**。

**这对本方案的影响**：多页面原型的路由由 AI 每次手搓实现，导致：

- 页面跳转行为在 REQ 之间不一致（有的用 `useState` 切换，有的改 hash）
- **浏览器前进 / 后退按钮行为不可控**——客户演示时点了返回，直接出戏
- `layout.md` 里写的路由在实现中未必被采用，无从校验

**建议**：引入 `react-router`（你已确认可小范围放开）。这会让「路由」从模板里的一个填空题变成可验证的事实。

列为**提案**，待你确认后实施。
