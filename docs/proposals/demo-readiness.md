# 落地方案 · 演示准备

> 对应评审报告 [`../review-2026-10-02.md`](../review-2026-10-02.md) §3.1 / §3.2 / §3.3 / §5.2
> 前提（已确认）：展示方式 = **本地跑起来给人看**，不涉及部署、导出、PDF。
> 目标：把「到客户面前打开 localhost」从一次赌博变成一个**有准备的流程**。

---

## 问题复述

`/rudder-commit` 之后到「打开浏览器演示」之间，目前是**完全空白**的。缺三样：

1. 演示动线（从哪进、按什么顺序、怎么收尾）
2. 演示前置准备（窗口尺寸、设备、浏览器）
3. 演示中的「出戏点」预案（mock 数据假、强制延迟、强制错误态）

其中**假数据真实度**是性价比最高的一项——它几乎零成本，但对客户观感的影响最大。

---

## 方案

### 1. 假数据真实度规范（**优先级最高**）

**现状**：宪法对 mock 的唯一要求是延迟区间和三态，对**数据内容**零要求。AI 默认生成 `张三` / `李四` / `测试数据1` / `item-001` / `2024-01-01`。

**后果**：客户第一眼就出戏。注意力从「你的方案怎么样」转移到「这东西是不是真的」——而后者对原型评估没有任何价值。

**改法**：在 `MASTER-PRD.md` 新增一节「**业务场景与假数据基线**」，在项目首次规划时（`/rudder-plan` 入口）由用户确认以下几项：

| 要确认的 | 示例 | 为什么重要 |
|---|---|---|
| **业务领域** | 工业品供应链 / 医美连锁 / 企业培训 | 决定所有文案的语感 |
| **典型用户与机构名** | 「华东机电」「张明 - 采购主管」 | 比「公司A」「用户1」可信 10 倍 |
| **真实感的数值区间** | 订单金额 5 千 ~ 80 万；交期 3 ~ 45 天 | 金额离谱会让懂行的客户出戏 |
| **状态流转的真实形态** | 草稿 → 待审核 → 已通过 → 已终止（**不是** `active`/`inactive`） | 状态词最能暴露「这是demo」 |
| **禁止出现的占位内容** | `Lorem ipsum`、`test`、`示例`、`xxx`、`2024-01-01` | 明确黑名单，AI 自查 |

**在 `plan.md` 模板的 Mock Schema 处增加一条约束**：

> Mock 数据必须符合 `MASTER-PRD.md` 的假数据基线；禁止使用 `Lorem ipsum`、`test`、`示例`、`xxx`、连续整数日期等占位内容。数据数量应足以填满首屏并有滚动余量（**列表类页面 ≥ 12 条**，否则客户无法判断滚动和分页表现）。

最后这条（**数量**）很容易被忽略但影响极大：只有 3 条数据的列表，客户根本感受不到「这是个有规模的产品」。

**成本**：几乎为零。只是一条写进规则的要求 + 入口处的一次确认。

### 2. 演示动线（Demo Script）

**改法**：在 `implement.md` 增加一节「**演示动线**」，由 Implement 阶段生成，内容包括：

- **开场页**：从哪个页面进、为什么（通常是业务价值最高的那一屏）
- **路径**：按顺序的 3-5 步，每步「点了哪里、说什么」
- **收尾**：回到哪个页面作为结束画面
- **兜底**：某个交互没生效时怎么办（跳到哪个页面继续）

**为什么由 AI 生成而不是用户自己想**：AI 有完整的页面结构信息，能判断出最有说服力的路径；用户在这个环节没有额外信息，靠临场发挥。

**同时给用户一段话术**，说明这是模拟数据——见下文 §4。

### 3. 演示前置检查清单

新增一份短文档（例如 `docs/demo-checklist.md`），`/rudder-commit` 完成后由 Agent 提示用户逐条确认：

- [ ] `npm run dev` 启动无报错
- [ ] 浏览器窗口宽度 ≥ 1280px（或已按目标演示设备调整）
- [ ] 已按演示动线走一遍，无空白页 / 无 `undefined` / 无 `NaN`
- [ ] 所有页面的 mock 数据非空（不是「测试中」状态）
- [ ] 假数据符合 `MASTER-PRD.md` 基线（抽查 3 条）
- [ ] 浏览器标签页标题、书签名已改成本项目名（`index.html` 的 title）
- [ ] 已准备好话术，说明数据为模拟

**最后一条容易漏但很关键**：`package.json` 的 `name` 是 `rudder-framework`，Vite 默认 title 会是它。客户在浏览器标签上看到 "rudder-framework" 会立刻出戏。

### 4. 演示态：强制延迟与强制错误态的处理

**这是本方案里唯一的规则冲突，必须由你定优先级。**

**冲突事实**：
- 宪法 §3 强制所有 service 模拟 **300-800ms** 延迟
- 宪法 §3 + implement 技能强制 Loading / Error / Empty 三态**必须实现**

**演示时的冲突表现**：
- 每次点击等 0.5 秒 → 客户觉得「卡」
- 点错了跳到「服务器开小差了」→ 客户觉得「不稳定」

而用户**并不知道这是强制要求**，会直接归因为产品质量。

**三个选项，我列出来但不替你选**：

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 保持现状 + 提前告知** | 演示前给用户一段话术：「页面切换的等待和错误提示是模拟真实网络，用来展示加载和异常处理的设计，实际接入后不会有」 | 零规则改动，零技术成本 | 依赖用户记得说；说漏了照样出戏 |
| **B. 加演示模式开关** | `src/components/` 提供一个 `DemoMode` 上下文，可关闭延迟、屏蔽随机错误。演示时打开 | 演示流畅稳定 | **直接违反宪法 §3**，需要明确「演示态优先于技术约束」的例外条款 |
| **C. 降低默认值** | 把强制延迟区间下调，或把错误注入改为需显式触发 | 折中 | 削弱了「评审时能看到加载态」的价值，与框架初衷冲突 |

**我的倾向是 A + B 的组合**：默认按宪法执行（评审场景看得到三态），但提供一个显式的演示开关，且**开关状态在页面上必须可见**（不能让客户以为开关是产品功能的一部分）。

**但这需要你明确宪法优先级，我不擅自修改。**

### 5. 图片 / 静态资源策略（评审报告 §5.2）

原型几乎必然有图：商品图、头像、公司 Logo、空状态插画。当前零规定，AI 只能外链随机图床——**演示时图裂或风格不搭**，是典型演示事故。

**建议的规则（待你确认具体选型）**：

- **公司 Logo / 品牌元素**：由用户在项目初始化时提供（`public/` 目录），**不外链**
- **商品图 / 头像**：优先本地 SVG 或占位图服务，**禁止外链随机图床**
- **空状态插画**：用统一的插画风格，**不要 AI 每次现画**（风格必然漂移）
- 所有外部资源必须**有降级方案**（加载失败时显示什么）

**这条依赖评审报告 §5.3 的放开项决策。**
