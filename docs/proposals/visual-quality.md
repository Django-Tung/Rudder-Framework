# 落地方案 · 视觉质量

> 对应评审报告 [`../review-2026-10-02.md`](../review-2026-10-02.md) §1.1 / §1.2 / §1.3 / §5.4
> 目标：让「好看」从**AI 当场自由发挥**变成**规则保证 + 可复现**。

---

## 问题复述

当前「UI 主风格」= `MASTER-PRD.md` 里两个自由文本占位字段。用户要回答「你要什么风格」，但他答不出来。规则体系里没有任何视觉约束，AI 每次生成都不一样。

---

## 方案：三层结构

把现在的「一句风格描述」拆成三层，每层都可执行、可校验：

```text
第 1 层  设计令牌 (Design Tokens)   ← 机器可读，AI 必须遵守
第 2 层  预设风格包 (Style Presets) ← 人类可选，新手回答的是「选哪个」
第 3 层  通用组件 (Shared Components) ← 跨 REQ 复用，杜绝风格漂移
```

### 第 1 层：设计令牌

在项目里定义一份唯一的令牌来源，AI 写任何 Tailwind class 时只能引用这里的值，不得写任意十六进制色值。

建议覆盖的令牌（**具体取值待定，见 §待确认**）：

| 类别 | 令牌示例 | 作用 |
|---|---|---|
| 色板 | `brand` / `surface` / `border` / `text` 各档位 | 消灭「随手一个 `#3b82f6`」 |
| 文字层级 | `title` / `subtitle` / `body` / `caption` 的字号 + 字重 | 建立视觉层级，是「好看」的最大来源 |
| 间距节奏 | 卡片内边距、页面边距、区块间距的固定档位 | 消灭留白混乱 |
| 圆角 | `sm` / `md` / `lg` 三档 | 消灭同款按钮三种圆角 |
| 阴影 | 一到两档 | 过深阴影是「廉价感」的主因 |
| 交互态 | hover / active / focus / disabled 的统一表现 | 演示时客户会点按钮 |

**落点建议**：`src/design/tokens.ts`（TypeScript 常量 + 推导出的 class 名映射）。

> ⚠️ **前置阻塞**：Tailwind CSS v4 的主题令牌必须写在 CSS 的 `@theme` 块里，而宪法 §2 规定 `src/index.css` 内容**仅限** `@import 'tailwindcss';`。
> **这条必须先由你决策**，否则第 1 层无法落地。见评审报告 §1.3。

**替代路线（若坚持不放开 index.css）**：不定义 `@theme`，改为在 `src/design/tokens.ts` 里集中导出常量，AI 写 class 时只能拼 `const CARD = 'rounded-lg border border-slate-200 p-6 bg-white'` 这类预置字符串。
代价：失去 Tailwind 的设计时一致性检查，且预置字符串散落在 TS 里不如 CSS 干净。**我不推荐，但列出以免决策被卡死。**

### 第 2 层：预设风格包（解决「新手答不出来」）

这是最关键的一层。当前 `rudder-plan` 给用户的是 `数据密集型工作台 / 轻量内容型 / 品牌主导 / 自定义`——**四个纯文字选项，用户无法在脑中成像**。

**改法**：改为**带图的选择**，每个预设至少包含：

- 风格名（面向用户的大白话，如「清爽后台」「深色数据大屏」）
- **一张截图或 ASCII 示意图**（放在 `docs/` 里，让用户能看）
- 适用场景（什么类型的客户 / 产品适合）
- 该预设对应的完整令牌取值

用户回答的问题从「你要什么风格」变成「**这两个里你要哪个**」——这是普通人能回答的问题。

**关键设计**：预设必须**可选可不选**。用户仍然可以说「你决定」，此时 Agent 应使用项目默认预设，并在 `MASTER-PRD.md` 记录「用户未指定，采用默认预设 X」。**这条能显著降低新手的决策成本**，同时不再留下「待用户确认」这种让流程卡死的状态。

### 第 3 层：通用组件

在 `src/components/` 建一组**跨 REQ 强制复用**的基础组件：`Button` / `Input` / `Select` / `Card` / `Table` / `Modal` / `Toast` / `Skeleton` / `EmptyState` / `ErrorState` / `Tabs` / `Pagination`。

并在宪法或 implement 技能中加一条：

> 同类交互元素**必须**使用 `src/components/` 中的组件；确需新建的，须说明为何现有组件不适用。

**理由**：多 REQ 迭代下，「好看」最容易崩的地方就是同款按钮在不同 REQ 里长得不一样。组件复用是唯一可靠解法——比任何设计规范都有效，因为它把规范变成了代码而不是文字。

> 顺带解决 5.4 的组件复用约束缺口。

## 验收标准（做完后应该怎么判定成功）

- [ ] 一个新手用户在不阅读任何文档的情况下，能在风格选择环节**做出选择或说出「你决定」**，不会卡住
- [ ] 连续做完 REQ-001 与 REQ-002 后，同类元素（按钮、卡片、标题）**外观完全一致**
- [ ] `rg '#[0-9a-f]{6}' src/` 在 `src/` 中**无结果**（颜色一律来自令牌）
- [ ] 同一项目重跑同一需求，视觉产出可复现

## 待你确认

1. **预设风格包做几个？** 我倾向 3-4 个（覆盖浅色 / 深色、密集 / 留白两端），过多会让新手选择困难、过少覆盖不了。 答: 3-4 个
2. **是否放开 `src/index.css`？** 见 §1.3。**这是硬阻塞，不解决则本方案无法落地。** 答: 开放
3. **令牌取值你来定还是我出草案给你审？** 涉及品牌观感，我不擅自定。 答: 给出草图
4. **通用组件由我先写一套基线，还是由第一个 REQ 的 implement 阶段边做边沉淀？** 前者统一但可能出现无人使用的组件，后者更贴合实际但需要强约束兜底。 答: 基础的可以用开源的, 其他的边做边沉淀
