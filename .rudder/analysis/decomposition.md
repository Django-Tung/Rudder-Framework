# 拆分判定 — 全局规则、用户任务与页面流程

> 本文件回答「**一段内容该归到 MASTER-PRD，还是该组成一个完整、连贯的 REQ**」。
> 产物结构见 [`analysis.md`](analysis.md)，拆分后的依赖问题见 [`dependency.md`](dependency.md)。

## 1. 拆分单位与归宿

| 类别 | 判定 | 归宿 |
|---|---|---|
| **全局规则 / 术语** | 跨需求共享，或定义了所有需求都要遵守的约束 | `requirements/MASTER-PRD.md` 的「全局业务规则 / 术语表」 |
| **候选 REQ（用户任务 / 连贯流程）** | 围绕一个用户目标，包含完成目标所需的相关页面与子功能，可形成完整、可验收的体验 | `pending_maps[i].requirements[]` 中的一个 REQ 条目 |

页面是判断体验边界的重要线索，**不是机械的一页一个 REQ**；单个功能操作也**不自动**成为一个 REQ。
一个候选 REQ 可以覆盖多个页面和多个子功能，只要它们共同完成一个用户任务或连贯业务流程。

## 2. 判定准则

按以下顺序判断：

1. **它是否是跨多个 REQ 共享的规则或术语？**
   - 是 → 归入 `MASTER-PRD.md` 候选全局规则 / 术语。
2. **识别用户目标和完成目标的主流程。** 从标题、页面名称、入口、操作、结果等证据中，找出用户如何开始、经过哪些步骤、最终得到什么结果。
3. **按完整任务归组页面与子功能。** 列表、详情、创建、编辑等若共同支撑同一任务，应优先放在同一个候选 REQ；同一页面里的多个操作若共同构成一个闭环，也不按操作拆散。
4. **检查拆分后的体验是否仍然完整。** 若拆开会造成入口、上下文、关键步骤或结果孤立，或需要拼接多个 REQ 才能完成目标，应合并。
5. **检查是否需要拆分过大的候选。** 若用户目标、入口、结果和验收可以彼此独立，且拆分后各自仍形成完整体验，可拆成多个候选 REQ；不能只因页面不同或功能名称不同就拆分。
6. **页面边界不明确时不猜。** 将页面关系、用户目标或拆分边界标记为待确认，提出中文问题；必要时先保留为一个较完整的候选，交由人工确认。

### 2.1 边界示例

| 内容 | 判定 | 理由 |
|---|---|---|
| 「金额一律保留两位小数，四舍五入」 | 全局规则 | 跨功能共享的计算约束，无法单独验收 |
| 「所有列表页默认每页 20 条」 | 全局规则 | 跨功能的展示约定 |
| 「系统使用 RBAC 权限模型」 | 全局规则 | 架构级约束，横切所有功能 |
| 「用户管理：查看用户列表、搜索、查看详情并编辑用户」 | 一个候选 REQ | 多个页面和操作共同完成用户管理任务，应保持页面与流程连贯 |
| 「报表中心：筛选报表、查看结果并导出」 | 一个候选 REQ | 筛选、结果和导出共同构成完整的报表使用流程 |
| 「用户管理」与「报表中心」有独立入口、目标和结果 | 两个候选 REQ | 两者可分别形成完整体验与验收，不应仅为视觉统一而合并 |

## 3. 澄清问题强制要求

**判定模糊时，Agent MUST 标记为待 Plan 确认并输出结构化问题，MUST NOT 擅自猜测补全。**

具体要求：

1. **记录不确定性**：可以先放入候选 REQ 或候选规则，但必须标记待 Plan 确认。
2. **输出结构化澄清问题**：每条为可回答的封闭式或开放式问题，用**中文**。
3. **等待人工回答**后再继续拆分。
4. `analysis.md` 的「待 Plan 确认」按需记录问题；详细澄清在 `/rudder-plan` 阶段完成。拆分批准只确认粗粒度分组，不代替 Plan 对用户流程、页面关系和验收边界的确认。

### 3.1 UI 主风格确认

`/rudder-import` 是项目的批量入口，`/rudder-plan` 是项目的增量入口；两者首次运行都必须确认项目级 UI 主风格，并记录到 `requirements/MASTER-PRD.md`。后续运行必须展示当前风格并由人确认沿用或调整。

UI 主风格属于项目级决策，不得由 Agent 根据需求文档自行推断。没有人工确认时，入口只能提出选项和问题，不能写入正式 `analysis.md`、`pending_maps` 或完整 `plan.md`。

## 4. 拆分产物写入 `pending_maps`

拆分结论写入 `requirements/MASTER-PRD.md` frontmatter 的 `pending_maps` 字段（**列表**）：

```yaml
pending_maps:
  - imp: IMP-20260922-001          # 对应 IMP-ID
    status: DRAFT                  # DRAFT | APPROVED
    created_at: 2026-09-22
    requirements:
      - id: REQ-001
        title: 用户登录
        priority: high
        dependencies: []
      - id: REQ-003
        title: 登录审计
        priority: medium
        dependencies: [REQ-001]
```

**`pending_maps` 是列表**，不是单个对象——多个 IMP 并存时各自持有独立的 `status`，
不会被后一次导入覆盖。

## 5. 批准与收尾

1. IMP 在 `analyzed` 状态**不得**自动产出 REQ 目录。
2. `/rudder-import` **内部暂停**，展示拆分结果（REQ 清单、标题、依赖关系）并请人工确认（中文）。
3. 人工确认后：该条目 `status` → `APPROVED`，为其中**每个** REQ 创建目录与 6 个文档（含 `layout.md` 模板），
   IMP 的 `metadata.yaml.status` → `approved`。
4. **立即从 `pending_maps` 移除该条目**——REQ 此后由 `AUTO-INDEX` 承接，
   **不得在两处同时登记**。

> 批准点是 `/rudder-import` 命令**内部的暂停**，**不是**一个独立的批准命令。
> 这与 `/rudder-plan` 等待"PRD 批准"的既有交互范式一致。

## 6. 路径 B 跳过拆分

路径 B（人驱动增量）**不经过** `pending_maps`：直接创建 REQ 目录，`deps` 由**人**填写，
`AUTO-INDEX` 的「来源」列记为 `人工登记`。因此路径 B 的第一个批准点是 `plan.md` 的 `APPROVED`。
