# 可用性评审：面向「不懂前端的业务人员」的原型产出

| 项目 | 内容 |
|---|---|
| 评审日期 | 2026-10-02 |
| 评审对象 | Rudder Framework 当前状态（分支 `feat/v1.0`） |
| 评审目标 | 该框架能否让**不熟悉原型制作的产品 / 业务人员**，借助 AI 产出**好看、符合需求、能展示给客户**的原型 |
| 已确认前提 | ① 目标用户 = 产品 / 业务人员，不懂前端；② 展示方式 = 本地跑起来给人看，不需要部署 / 导出；③ 技术栈白名单**可小范围放开**，放开项以「提案」标注 |

---

## 0. 结论摘要

框架在**流程可控性**上做得相当扎实——状态机、门禁、依赖闭包、证据留痕、技能单源投影，这些对「AI 会跑偏、会吹牛、会乱改」的对冲是有效的，本报告不质疑其设计。

但对着「好看 / 符合需求 / 能展示给客户」这三个目标逐条比对：

| 目标 | 现状判定 | 说明 |
|---|---|---|
| **好看** | ❌ 无约束 | 规则体系里**没有任何视觉约束**。技术栈约束了「用什么写」，但没约束「长什么样」 |
| **符合需求** | ⚠️ 半闭环 | 需求 → 文档 → 代码的链路完整，但**没有任何一步验证「做出来的页面 = 文档里写的需求」** |
| **能展示给客户** | ❌ 无准备 | 演示就是 `npm run dev` 打开 localhost。没有演示动线、没有假数据真实度要求、没有演示态约定 |

三个目标里，**「好看」是完全空白**，「符合需求」缺最后一环的验证，「能展示给客户」缺演示前的准备。

> 一句话概括：Rudder 现在的设计假设是「用户能判断产出质量」，因此把所有检查都做成了**结构性校验**（文件在不在、状态对不对、AC 有没有被任务覆盖、代码能不能编译）。
> 而目标用户恰恰**不具备这个判断力**——他看得懂页面好不好看，但看不懂 `check:req` 拦住了什么。
> 这是本框架与目标用户之间最根本的一处错配，也是下面绝大多数问题的共同根因。

## 1. P0：阻断「好看」

### 1.1 视觉规范完全缺席 —— 最核心的问题

**证据**：

- [`.rudder/constitution.md`](.rudder/constitution.md) §2「前端技术栈（STRICT）」只约束 React / TS / Tailwind / Zustand / Lucide，**无一条关于颜色、字体、间距、圆角、阴影、图标尺寸、组件形态的规则**。
- [`requirements/MASTER-PRD.md`](requirements/MASTER-PRD.md) §1「UI 主风格」全文只有两个字段：
  - `- 风格名称：待用户确认`
  - `- 风格描述：待用户确认`
- [`skills/rudder-plan.md`](skills/rudder-plan.md) L33 给用户的选项是：`数据密集型工作台 / 轻量内容型 / 品牌主导 / 自定义`。

**问题**：这四个选项对不懂前端的用户**没有可操作性**。用户无法回答「我要品牌主导还是轻量内容型」——他不理解这些词对应到什么视觉结果，也无法判断哪个适合他的客户。他大概率会随便选一个或说「你决定」，然后 AI 自由发挥。

后果是连锁的：

1. AI 每次生成的配色、圆角、间距、按钮形态都不一样 → **REQ 之间视觉割裂**。做完 REQ-001 再做 REQ-002，风格漂移，客户一眼看出是拼的。
2. 「好看」没有任何判定依据 → 好和坏都由 AI 当场决定，不可复现、不可交接、不可 Review。
3. MASTER-PRD 里的术语表（§3）是全仓库**唯一**能提升质感的东西，但它只管文字，不管视觉。

**这是「好看」三个字的唯一入口，目前它是空的。**

> 详见 [`proposals/visual-quality.md`](proposals/visual-quality.md)。

### 1.2 没有任何可参照的样例（锚点缺失）

**证据**：

- `src/` 下只有 `.gitkeep` 占位文件，**零业务代码**。
- `requirements/` 下只有 `MASTER-PRD.md`，没有 `archive/`，**没有任何一个完整的 REQ 样例**。

**问题**：新手用户打开项目，看到的是一份 370 行的 README 和一套规则，看不到任何「别人做出来长什么样」。AI 同样没有锚点——`rudder-plan` / `rudder-implement` 技能里没有任何「参考这个已有页面」的指引。

**后果**：整个项目是空心的。用户不知道终点长什么样，AI 也不知道参照物在哪。对「新手」尤其致命——新手最大的优势本该是「照着例子学」。

### 1.3 色彩令牌与「唯一 CSS 文件」规则冲突（实施障碍，需先决策）

**证据**：

- [`.rudder/constitution.md`](.rudder/constitution.md) §2：「唯一允许存在的 CSS 文件是 `src/index.css`（Tailwind 入口，内容**仅限** `@import 'tailwindcss';`）」。
- Tailwind CSS v4 的主题令牌（自定义色板、字体、圆角、间距）**必须**通过 CSS 的 `@theme` 块定义。

**问题**：一旦要做统一视觉规范，就必须定义主题令牌；而定义令牌就要往 `index.css` 里写 `@theme`，这**直接违反现有宪法条款**。

**这条是「1.1 的视觉规范」能否落地的前置阻塞**。必须由你决策：放开 `index.css` 的内容限制，还是走其他路线（见落地方案文档）。我不擅自选择。

## 2. P0：阻断「符合需求」

### 2.1 AC 从未被拿去和真实页面对账

**证据**：

- [`README.md`](README.md) §4 阶段 2 L215-218：Implement 的检查是 `npm run typecheck` / `lint` / `build` / `check:skills` / `check:req`。
- `check:req` 的职责（README L79）：「断言 tasks 勾选一致性（I1/I2）、`README.md` 顶层状态推导一致、依赖闭包与 `STALE` 一致」。

**问题**：I1 只断言「每条 AC 都被某个 task 引用」，I2 只断言「`implement.md` 已 `COMPLETED` 时 `tasks.md` 无未勾选项」。

这两条校验的是**文档之间的引用完整性**，不是**代码与需求的一致性**。因此完全可能出现：

> AC-3 写「列表为空时显示空状态插画和『还没有供应商，去添加』引导按钮」→ AI 拆成 task #7 并勾选 → 代码里画了一个光秃秃的文字「暂无数据」→ 5 条 npm 命令全绿 → `check:req` 通过 → **但页面不满足 AC-3**。

整条链路**没有任何一步要求打开浏览器看一眼**。AI 不看，用户也没被组织去看。

**后果**：对不懂前端的用户尤其致命——他恰恰是最依赖这套检查的人，却完全无法判断检查通过意味着什么；而 AI 可以「全部完成」却做偏。这是本框架最需要补的一环。

### 2.2 `layout.md` 的 ASCII 线框不可执行

**证据**：[`.rudder/templates/layout.md`](.rudder/templates/layout.md) 全文是文本线框 + 组件映射表，要求画桌面端与移动端。

**问题**：线框只能表达**区域划分**，无法表达**视觉质感**——间距是否舒服、层级是否清晰、留白是否得当、对齐是否整齐。而「好看」的判断 90% 在这些线框表达不了的地方。

同时模板 L49 要求「说明桌面布局在窄屏下的隐藏、折叠、重排行为」，但：

- `plan.md` 模板里「响应式要求」只是 §4 的一个普通条目；
- `constitution.md` 无响应式强制条款；
- `rudder-implement` 技能的检查步骤里没有响应式验证；
- 没有任何校验脚本检查窄屏行为。

**后果**：多页面 / 窄屏是「看起来像不像正式产品」的高感知项，目前完全靠 AI 自觉。

## 3. P1：阻断「能展示给客户」

（按你的确认，展示方式就是本地跑起来给人看，因此不涉及部署与导出。以下只谈**演示前需要准备什么**。）

### 3.1 演示前没有准备环节

现在从 `/rudder-commit` 到「打开浏览器演示」之间是空的。缺三样东西：

| 缺什么 | 现状 | 演示时会发生什么 |
|---|---|---|
| **演示动线** | 无任何要求 | 用户不知道从哪个页面进、按什么顺序点，中途卡住要现想 |
| **窗口尺寸 / 设备** | 无规定 | 客户看到的是自己笔记本上一个被拉伸得奇形怪状的窄窗口 |
| **演示前置检查** | 无 | 到客户面前才发现某个页面 mock 数据是空的 |

### 3.2 假数据真实度没有任何要求

**证据**：宪法要求 mock 延迟 300-800ms、三态齐全，但**对 mock 数据的内容**零要求。

**后果**：AI 默认生成的 mock 是 `张三`、`李四`、`测试数据1`、`item-001`、`2024-01-01`。客户看到的第一屏就出戏——这比做得不够好看更致命，因为它直接暴露「这是个演示」，让客户把注意力从「你的方案」转到「这东西是不是真的」。

**反过来**，如果 mock 数据是一个真实可信的业务场景（真实的行业词汇、合理的金额和日期分布、有业务含义的状态流转），即使功能不完整，客户也愿意认真评估方案。**假数据是原型质量里性价比最高的一项投入，目前框架对此完全沉默。**

### 3.3 「强制延迟 + 强制错误态」与演示冲突，且未告知用户

**证据**：[`.rudder/constitution.md`](.rudder/constitution.md) §3 强制 300-800ms 延迟；§3 强制 Loading/Error/Empty 三态。

**问题**：客户演示时，点一下按钮等 0.5 秒、点错了跳到「服务器开小差了」——但这是**强制要求**，不是 bug。用户看到时并不知道这一点，会误判产品不稳定。

框架没有「演示态」这个概念，也没有任何地方提示用户在演示前该做什么。

> 这条不是要取消强制约束（它们对需求评审有价值），而是需要**在演示前有一个明确的处理方式**，并让用户知道。属于决策项，见 [`proposals/demo-readiness.md`](proposals/demo-readiness.md)。

## 4. P1：阻断新手上手

### 4.1 概念密度超出目标用户的承受范围

一个业务人员要在第一次使用前理解的东西：

- **7 个斜杠命令**，且要区分 `/rudder-plan` vs `/rudder-plan-confirm` vs `/rudder-change` vs `/rudder-adjust`（后两个的差别是「契约变没变」，README L346 用了一整段解释）
- **两条入口路径**（Import / Plan）及其分岔逻辑
- **IMP 管道** 4 个状态（`imported → analyzed → approved → archived`）
- **每个 REQ 6 个文档 + 1 个 IMP 目录 4 个文件**
- **双层状态**：顶层 4 态 × 产物 7 态 × `stale` 布尔

[`docs/getting-started.md`](docs/getting-started.md) 是一份**平铺的操作手册**（10 节，按顺序读完约 300 行），它告诉用户「怎么做」，但没告诉用户「**现在该做什么**」和「**出错了怎么办**」——没有决策树、没有「如果 AI 没按预期做怎么办」。

对于一个不懂前端的业务人员，**状态名本身就是噪音**：`IMPLEMENTING` / `IMPLEMENTED` / `COMMITTED` / `OUTDATED` / `STALE` 这套体系对他的价值几乎为零，但他每天都会在对话里看到它们。

> 这套体系本身设计得很好，我不建议削弱它。建议的是**在用户侧加一层人话视图**（见 [`proposals/novice-onboarding.md`](proposals/novice-onboarding.md)）。

### 4.2 教程里的占位符与实际不一致

**证据**：[`docs/getting-started.md`](docs/getting-started.md) L44-45：

```bash
git clone <项目地址>
cd ProtoSource
```

- `<项目地址>` 是占位符，无实际地址。
- `ProtoSource` 与实际仓库目录名 **`Rudder-Framework`** 不一致。

**后果**：新手第一条命令就要改。**第一印象损失最大的地方恰好是教程的第 2 步。**

### 4.3 README 的目录树列出了不存在的目录

**证据**：[`README.md`](README.md) §2 L43-44 列出了：

```text
│   ├── verification/
│   ├── review/
```

**实际**：`.rudder/` 下只有 `README.md` / `agents` / `analysis` / `constitution.md` / `implementation` / `import` / `requirement` / `templates` / `workflow`。这两个目录**不存在**。

同类问题：README L49 称 `skills/` 下是「rudder-<name>.md × 7」，实际确为 7 个，一致；但 README L81 称 `sync:skills` 生成「14 个投影文件」，`.claude/commands/` 7 个 + `.hermes/skills/` 7 个 = 14，一致。**只有 verification / review 两处是失效引用。**

### 4.4 Hermes 双投影增加了不必要的认知负担

`skills/` 单源投影到 `.claude/commands/` 和 `.hermes/skills/`，对使用者来说是 14 个文件而非 7 个，且新手几乎不可能用到第二个 runtime。这不是 bug，但它是「规则已经覆盖不到全部注意力的地方」的一个例证。

## 5. P2：一致性与可维护性

### 5.1 没有路由库，但模板要求写「路由」

**证据**：

- `package.json` 的 `dependencies` 只有 `lucide-react` / `react` / `react-dom` / `zustand`，**无路由库**。
- [`.rudder/templates/plan.md`](.rudder/templates/plan.md) §「页面结构与布局图」要求填写「**页面/路由**：[完成本 REQ 目标所需的页面及路由]」。
- [`.rudder/templates/layout.md`](.rudder/templates/layout.md) §「页面与路由」表格有一列叫「路由」。

**问题**：模板强制要求写路由，但技术栈里没有路由库。多页面原型的路由只能 AI 手搓，每次实现方式不同（`useState` 切换 / hash 手写 / History API 直接操作），页面间跳转、深链接、浏览器前进后退行为都不一致。

**这直接伤「符合需求」和「好看」**：客户点完 A 页想退回 B 页，如果行为诡异，专业度立刻归零。

> 你已确认技术栈可小范围放开，此项列为提案（见 5.3）。

### 5.2 没有图片 / 静态资源策略

原型几乎必然涉及图片：商品图、用户头像、公司 Logo、插画（尤其 3.1 里空状态需要的「插画」）。当前规则对图片**零规定**：

- 不许外链第三方占位图服务？那用什么？
- 用本地 SVG？由 AI 画？由用户提供？
- 客户品牌 Logo 怎么处理？

AI 当前只能自由发挥，结果通常是外链到随机图床——**演示时图裂了或者图片风格完全不搭**，是「演示事故」的常见来源。

### 5.3 需要你确认的放开项（提案，非结论）

按你的授权，以下均为**待你拍板的提案**，我不会直接改动 `package.json`：

| 提案 | 理由 | 代价 |
|---|---|---|
| 引入 `react-router` | 模板已强制要求写路由；统一多页跳转行为 | 增加一个依赖（轻量，无 UI 侵入） |
| 放开 `src/index.css` 允许 `@theme` 令牌块 | Tailwind v4 定义主题必须走 CSS，否则统一视觉无落地 | 修改宪法 §2 现有条款 |
| 允许占位图 / 本地 SVG 资源 | 见 5.2 | 需要新增一条资源规则 |

### 5.4 其他小项

- **无中文文案规范**：MASTER-PRD §3 有术语表（这是个好资产），但没有错误提示、按钮动词、金额 / 日期格式的写法约定。客户看到的是文案，文案不统一在演示中很扎眼。
- **无组件复用约束**：宪法只说「`src/components/` 通用组件」，没有强制「同款按钮必须复用同一个组件」。多 REQ 迭代下最容易出现同款按钮三种圆角。
- **`implement.md` 证据是给谁看的**：质量检查的完整输出记在文档里，对业务用户是纯噪音（终端报错他看不懂），他真正需要的是「这次做完了什么、怎么验证」。

## 7. 待你确认的问题清单

以下是我**没有擅自补充**、需要你拍板的地方。按影响面排序：

1. **视觉规范怎么做？** 给用户 3-4 个**带截图和效果说明**的预设风格包让选？还是给一套默认现代风格 + 允许调整？——这决定了新手能不能答得上这个问题。
2. **是否放开 `src/index.css`？** 不放开就无法定义 Tailwind v4 主题令牌，等于视觉规范无法落地。（§1.3）
3. **是否引入 `react-router`？**（§5.1，提案）
4. **图片 / 资源策略怎么定？** 外链占位图服务 / 本地 SVG / 由用户在导入时提供素材？客户 Logo 怎么处理？（§5.2）
5. **演示态怎么处理强制延迟与错误态？** 加一个演示模式开关（与宪法 §3 冲突，需定优先级）？还是在演示前给用户一份「这些是模拟」的说明话术？（§3.3）
6. **是否要保留 Hermes 双投影？** 若暂不需要用户群，可先只保留 Claude Code 投影，减少 7 个文件。（§4.4）
7. **是否入库一个示例 REQ 作为参照锚点？** 这会占用一次完整生命周期，但能让新手和 AI 都有「长什么样」的标尺。（§1.2）
