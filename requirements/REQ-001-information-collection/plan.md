# 信息采集与采集动态

## 业务背景与非目标

投研人员需要统一查看政策、公告、项目舆情和竞品动态，减少分散信息源带来的遗漏，并通过采集动态追溯信息来源。本需求提供信息进入系统的模拟能力，为后续解析、研判和项目管理提供统一输入。

本期使用模拟信息源、模拟采集结果和模拟采集规则，不接入真实公众号、公告平台或外部抓取服务。动态本体推理数据通过模拟适配器提供，后续预留 API 接入边界。多模态内容的解析和结构化提取属于 REQ-002；研判结论和风险判断属于 REQ-003。

## 用户故事与场景

- 作为投研人员，我希望按时间和类型查看采集动态，以便快速发现近期信息。
- 作为投研人员，我希望按项目、情感标签和信息类型筛选动态，以便聚焦具体项目和风险线索。
- 作为投研人员，我希望打开动态详情查看来源、正文、附件和原文链接，以便复核信息。
- 作为管理员或配置人员，我希望维护信息源、关键词、黑名单和采集时间范围，以便调整采集范围。
- 作为投研人员，我希望查看动态本体产生的关联链路，以便理解未直接命中关键词的信息为何关联到项目。

## 验收标准

### AC-1: 采集动态列表

给定系统存在模拟采集数据，当用户进入采集动态页面时，应按采集时间倒序展示动态条目，并显示信息源、标题、采集时间、类型标签、情感标签和关联项目。

### AC-2: 多维筛选

给定用户在采集动态页面，当选择时间范围、信息类型、情感标签或关联项目筛选条件时，应只展示符合条件的模拟动态，并支持清除筛选恢复列表。

### AC-3: 信息详情

给定用户打开一条采集动态，当详情抽屉展开时，应展示信息来源、发布时间、采集时间、正文全文、原文链接、图片信息和附件信息；无对应内容时显示明确的空值状态。

### AC-4: 去重归并

给定模拟数据包含同源重复信息，当系统加载采集结果时，应将重复条目归并为一条，并保留可追溯的原始来源列表或来源数量。

### AC-5: 采集规则配置

给定用户具有配置权限，当用户维护信息源启用状态、关键词、黑名单和采集时间范围时，应能保存模拟配置；普通投研人员可以查看配置结果但不能修改。

### AC-6: 动态本体关联

给定采集条目未直接命中项目关键词但模拟动态本体返回关联结果，当用户查看详情时，应展示“触发方式—因果关联节点—关联项目—推理置信度”的完整推理链；没有动态本体关联时不展示虚构链路。

### AC-7: 三态反馈

给定采集动态数据处于加载中、返回空结果或请求失败状态，页面应分别展示 Loading、Empty、Error 状态，并提供符合当前状态的反馈或重试入口。

## UI/UX 三态规格

- Loading：列表区域显示稳定尺寸的加载占位，筛选条件保持可见但暂不提交新查询。
- Empty：显示当前筛选条件下暂无采集动态，并提供清除筛选操作。
- Error：显示采集动态加载失败原因和重试按钮，不清空用户已选择的筛选条件。

## 主 UI 风格

沿用项目确认的“数据密集型投研工作台”，本 REQ 不设置例外。界面优先支持高密度扫描、组合筛选、来源追溯和详情复核。

## 技术契约与数据模型

### 数据类型

- `InformationSource`：`id`、`name`、`category`、`enabled`、`keywords`、`blacklist`、`timeWindow`、`frequency`。
- `CollectionItem`：`id`、`sourceId`、`sourceName`、`title`、`publishedAt`、`collectedAt`、`type`、`sentiment`、`projectName`、`content`、`originalUrl`、`images`、`attachments`、`duplicateGroupId`、`sourceCount`、`ontologyReasoning`。
- `OntologyReasoning`：`trigger`、`nodes`、`relatedProject`、`confidence`；无关联时为 `null`。
- `CollectionFilters`：`timeRange`、`type`、`sentiment`、`projectName`。

### Service 与 Mock 约定

- UI 只调用 `src/services/`，不得直接引用 `src/mocks/`。
- `getCollectionItems(filters)`、`getInformationSources()` 和 `updateInformationSource(source)` 均返回 `Promise`。
- Mock service 使用 300-800ms 的 `setTimeout` 模拟网络延迟，并提供可复现的 Loading、Empty 和 Error 场景。
- 动态本体通过 `getOntologyReasoning(itemId)` 的模拟适配器提供；后续真实 API 接入不得改变 UI 使用的 `OntologyReasoning` 契约。
- 过滤和去重归并在 service 层完成，组件只负责展示和交互状态。

### 状态管理

Zustand store 管理采集动态、信息源、筛选条件、加载状态、错误信息和详情抽屉状态；页面不得直接管理跨组件共享的采集数据。
